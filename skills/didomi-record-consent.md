# Record a consent decision in Didomi

Didomi's consent event is the record of truth. Writing one both stores the audit
trail and updates the user's current consent status — there is no separate
"update the user" call.

> Didomi's OpenAPI declares **no `operationId` on any of its 190 operations**, so
> every step below is identified by METHOD + path. Do not look for operationIds;
> there are none to look up.

## 1. Get a token

```
POST https://api.didomi.io/v1/sessions
Content-Type: application/json

{"type": "api-key", "key": "<API_KEY>", "secret": "<API_SECRET>"}
```

Read `access_token` from the response and send it as
`Authorization: Bearer <access_token>` on every later call.

- The token is valid for **3600 seconds**. Cache it. Do not mint one per request.
- Bad credentials return **400**, not 401.
- A missing or expired token on any other call returns **401**.

## 2. Record the event

```
POST https://api.didomi.io/v1/consents/events?organization_id={organization_id}
Authorization: Bearer {token}
Content-Type: application/json
```

Body, per the Consents API V2 Event schema:

```json
{
  "user": { "organization_user_id": "user@example.com" },
  "regulation": "gdpr",
  "consents": {
    "purposes": [
      { "id": "geolocation_data", "enabled": true }
    ],
    "vendors": { "enabled": [], "disabled": [] }
  },
  "metadata": {}
}
```

Rules that will bite you:

- **`id` and `created_at` are generated by the API** if you omit them. Supply
  them only when back-dating an import.
- **Purpose and preference IDs are validated.** Since 18 January 2022 Didomi
  rejects IDs that do not exist (or never existed) in your organization. Fetch
  the catalogue with `GET /metadata/purposes` first rather than guessing.
- **`enabled: null` is meaningful** — it means the user made no choice for that
  purpose, which is different from `false`. Do not coerce it.
- **`regulation` defaults to GDPR** if you omit it, both on write and on read.
  If your organization has multi-regulation enabled, always set it explicitly.
- Add `$disable_integrations=true` to the query string when importing consents
  that already exist in your downstream systems, so the write is not forwarded
  to your integrations.

## 3. Confirm the status

```
GET https://api.didomi.io/v1/consents/events/{id}
Authorization: Bearer {token}
```

An event is either `confirmed` or `pending_approval`. Poll `GET
/consents/events/{id}` until it is `confirmed` before treating the decision as
applied. To list, use:

```
GET /consents/events?organization_id={org}&organization_user_id={id}&status[$in]=confirmed&status[$in]=pending_approval
```

Without a `status` filter only **confirmed** events are returned.

## Rate limits

The `/consents/*` routes are **exempt** from Didomi's general limit — record as
fast as you need to. Two exceptions:

- `GET /consents/users` and `GET /consents/users/{id}` with
  `$include_full_tree=true` fall back under the limit.
- Every other route in the API is capped at **100 requests / 15 seconds, per
  organization** (shared across all of that organization's API keys).

Read the `RateLimit: limit=…, remaining=…, reset=…` header on every response and
throttle before you hit 429. On 429, honour `Retry-After` (seconds).

## Errors

Didomi returns one envelope everywhere — it is **not** RFC 9457:

```json
{"code": 400, "name": "BadRequest", "message": "…", "errors": {}}
```

Branch on `code`; `name` adds nothing the status does not already tell you.

## ⚠️ There is no idempotency key

Didomi publishes **no** `Idempotency-Key` header and no replay window. If
`POST /consents/events` times out you cannot safely retry it — a blind retry may
record the same consent decision twice.

Mitigation: put your own correlation value in the free-form `metadata` object
(e.g. `metadata.client_event_id`), and before retrying, query
`GET /consents/events?organization_id={org}&metadata.client_event_id={value}`.
Didomi supports dotted metadata paths in filters (it documents the same notation
for filtered deletes). This is a workaround, not a guarantee.

## Downstream

A successful write emits an `event.created` webhook to your organization's
configured endpoint, and (if the user record changed) `user.updated`. See
`asyncapi/didomi-webhooks.yml`.
